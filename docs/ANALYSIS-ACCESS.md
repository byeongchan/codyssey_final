# 분석 인증·작업 소유권·요청 한도

코드·테스트 소스·OpenAPI를 작성했다. 설치·서버 실행·빌드·테스트는 수행하지 않았다. 실제 Gemini 호출은 아직 없다.

## 변경된 계약

다음 3개 API 모두 Firebase Emulator 로그인 토큰이 필요하다. 경로는 유지한다.

- POST /api/v1/products/{id}/analysis-jobs: 본인 작업 생성 또는 본인의 같은 입력 작업 재사용
- GET /api/v1/analysis-jobs/{jobId}: 본인 작업 상태 조회. 타인의 ID는 없는 작업과 같은 404
- GET /api/v1/products/{id}/analysis: 본인의 유효 캐시 조회. 미생성·실패·만료는 404

상품 목록·상세·판매처·가격 이력은 공개 조회를 유지한다. 프론트엔드는 미로그인 시 분석을 요청하지 않고 로그인 버튼을 표시한다. 로그인·계정 전환 시 새 계정으로 요청하며 이전 폴링을 취소한다. 내부 키를 브라우저에 보내지 않는다. 분석 요청에는 기존 API 클라이언트의 토큰 갱신·같은 출처 제한을 적용한다.

작업 ID·입력 병합·캐시는 UID별로 분리한다. 같은 상품·같은 입력이라도 다른 계정은 별도 작업이다. 응답 dataVersion은 가격 근거 버전이며 UID가 아니다. 응답에 소유자 UID·이메일을 포함하지 않는다. 성공 응답은 no-store와 Vary: Authorization을 사용한다.

## 한도와 보관

실제 서버 시간 기준으로 사용자별 최초 요청부터 60초 동안 생성 POST를 5회 허용한다. 정확히 60초 경계에서 새 구간을 시작한다. 6번째는 429다. 존재하지 않는 상품은 한도 차감 전에 거부한다. 캐시 적중·진행 중 작업 재사용·실패 재시도도 POST이므로 차감한다. 대기열/전역 작업 한도로 접수 실패해도 이미 차감한 회수는 환급하지 않는다. GET 폴링·캐시 조회는 차감하지 않는다.

카운터는 users/{uid} 루트의 analysisWindowStart·analysisCount에 Firestore 트랜잭션으로 저장한다. fixture 기준 시각과 무관하며 API 재시작 후에도 유지된다. 저장소 장애 때 메모리 한도로 대체하지 않고 요청을 실패시킨다. 계정 삭제 중에는 409로 차단하고 기존 계정 삭제의 루트 덮어쓰기에서 카운터도 제거한다. 별도 하위 컬렉션은 추가하지 않았다.

기존 공통 429 응답의 Retry-After=5는 재확인 안내이며 남은 구간의 정확한 시간은 아니다. 최초 POST 후 60초까지 기다려 검증한다. 일일 예산·유료 모델 비용 제한·GET 호출 제한은 아직 없다.

작업 실행은 여전히 현재 프로세스 메모리다. 동시 실행 2개·대기 16개·기록 최대 1000개, 완료/실패 후 1시간 보관, 성공 캐시 실제 시간 15분과 근거 만료 검사를 유지한다. API 재시작 후 작업 ID·캐시는 없어져 404가 되지만 카운터는 에뮬레이터에 남는다. 여러 API 프로세스는 카운터만 공유하며 작업·캐시는 공유하지 않는다. 실서비스 분산 큐·재시작 복구는 후속 단계다.

계정 삭제 후 큐에 접수된 계산은 메모리에서 끝날 수 있지만 개인 Firestore 쓰기를 추가하지 않는다. 삭제된 계정 토큰은 기존 인증 검증에서 차단된다. 메모리 작업 취소·분산 작업 삭제는 후속 범위다.

## 실행과 사용자 직접 검증

1. README/FIREBASE.md에 따라 Auth·Firestore Emulator, API, FastAPI, 프론트엔드를 실행한다. 별도 분석용 환경 변수는 없다. FastAPI와 API의 INTERNAL_API_KEY는 기존처럼 같게 유지한다. 미로그인 상품 화면에서 가격·차트는 보이고 분석은 로그인 안내여야 한다.
2. Alice로 로그인하여 상품 상세에서 분석을 생성한다. 완료 후 다시 요청하면 같은 계정의 유효 작업을 재사용해야 한다. GET 폴링은 생성 횟수를 추가하지 않는다.
3. Bob으로 전환하고 Alice의 jobId를 Bob 토큰으로 조회하면 404여야 한다. Bob이 생성하지 않은 캐시는 404이고, 같은 상품을 생성하면 Alice와 다른 jobId여야 한다. 로그아웃·계정 전환 중 이전 응답이 표시되지 않아야 한다.
4. API 클라이언트 또는 브라우저 네트워크 도구에서 같은 계정으로 POST를 구간 내 6번 보낸다. 화면 자동 요청·401 이후 토큰 갱신 재전송의 성공한 POST도 포함해 계산한다. 첫 5번은 재사용할 수 있고 6번째는 429여야 한다. GET을 반복한 뒤에도 구간 만료 후 정상 접수되는지 확인한다.
5. 5회 사용 후 API만 재시작한다. 60초가 지나지 않았으면 생성은 계속 429여야 한다. 기존 작업 조회는 재시작으로 404다. 에뮬레이터는 계속 실행하여 카운터를 보존한다.
6. Firestore 중단 시 POST가 실패하고, 계정 삭제 진행 중에는 409로 생성이 차단되는지 확인한다. 이미 생성한 작업은 메모리이므로 조회될 수 있다. 전체 에뮬레이터를 중단하면 인증 자체가 실패할 수 있다.
7. 미인증 3개 API는 401이어야 한다. 타인 UID를 요청 본문·쿼리에 넣어도 소유자가 바뀌면 안 된다. 토큰·UID·이메일·내부 키가 분석 응답과 오류에 노출되면 안 된다.

수동 API 예시는 본인 개발 환경에서만 사용한다. 로그인 후 브라우저 네트워크 요청의 Authorization에서 본인 개발용 ID 토큰을 확인하여 아래 자리표시자를 대체한다. 토큰을 저장소·공유 문서에 기록하지 않는다.

```powershell
$analysisHeaders = @{ Authorization = 'Bearer <본인 개발용 ID 토큰>' }
$job = Invoke-RestMethod -Method Post -Headers $analysisHeaders 'http://127.0.0.1:8080/api/v1/products/sony-xm5-black/analysis-jobs'
Invoke-RestMethod -Headers $analysisHeaders "http://127.0.0.1:8080/api/v1/analysis-jobs/$($job.data.jobId)"
Invoke-RestMethod -Headers $analysisHeaders 'http://127.0.0.1:8080/api/v1/products/sony-xm5-black/analysis'
```

서버 테스트 소스는 UID별 분리·타인 404·캐시 격리·인증 선행·상한 초과 시 접수 차단·60초 경계·새 서비스 인스턴스의 저장 카운터 재사용·삭제 중 쓰기 차단을 추가했다. 에뮬레이터 동시 트랜잭션 경합과 실제 UI는 위 절차로 별도 검증한다.
