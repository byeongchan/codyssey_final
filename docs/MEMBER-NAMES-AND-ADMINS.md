# 표시 이름과 관리자 권한

## 표시 이름

서비스의 공식 표시 이름은 Firestore `users/{uid}.memberDisplayName`입니다. Firebase Authentication의 `displayName`을 직접 변경해도 서비스의 이름이나 관리자 권한은 바뀌지 않습니다. 향후 게시글·댓글 작성자 이름도 클라이언트 요청값이나 Firebase 이름을 그대로 저장하지 말고 이 서버 프로필에서 읽어야 합니다.

- 가입 완료 시 서버에 이름을 처음 등록합니다. 첫 등록 후부터 7일(168시간)이 지나야 변경할 수 있습니다.
- 다음 변경 가능 시각은 내 정보에 표시됩니다. 서버 시각과 트랜잭션으로 검사하므로 브라우저 시각 조작·동시 요청으로 우회할 수 없습니다.
- 같은 이름 재요청은 변경 시각을 연장하지 않습니다. 응답을 받지 못한 가입 완료 요청도 같은 이름으로 재시도할 수 있습니다.
- Unicode NFKC 정규화 후 2~24자의 문자·숫자·공백·밑줄·마침표·하이픈을 허용합니다.
- 관리자·어드민·운영자·운영진·운영팀·관리팀·공식계정·admin·administrator·moderator·staff를 포함한 이름을 차단합니다. 비교 시 대소문자·공백·구두점을 제거합니다. `Ad.min`, `관리 자`, 전각 `Ａｄｍｉｎ`도 차단합니다. 허용되지 않은 제어문자나 보이지 않는 문자도 차단합니다.
- 모든 유사 문자나 사칭 표현을 완벽히 식별하는 것은 아닙니다. 커뮤니티에서는 이름 외에 서버가 계산한 역할 배지를 사용해야 합니다.
- 기존 Firebase 이름은 자동으로 신뢰하거나 복사하지 않습니다. 기존 회원은 내 정보에서 표시 이름을 한 번 등록해야 합니다. 자동 이관 때문에 금지 이름이 남거나 변경 시각을 잘못 추정하는 것을 방지합니다.
- 권한과 변경 시각을 이름 수정 본문에 넣으면 요청을 거부합니다. 브라우저 Firestore 직접 쓰기는 기존 규칙에서 금지되어 있습니다.

규칙은 Java `DisplayNamePolicy`가 단일 원본이며 프론트엔드는 공개 정책 API를 읽어 같은 규칙으로 안내합니다. 최종 판정은 서버에서 다시 합니다.

## Firebase에서 관리자 지정

권한의 단일 원본은 Cloud Firestore `serviceAccess/administrators` 문서의 `uids` 문자열 배열입니다. `.env`의 `ADMIN_UIDS`는 사용하지 않습니다. 남아 있는 값은 삭제해도 됩니다. `OPERATIONS_UIDS`는 기존 수집 운영자 권한이므로 별개로 유지합니다.

최초 등록은 Firebase 프로젝트 소유자가 콘솔에서 수행합니다.

1. 서비스에 가입하고 이메일 인증을 완료합니다.
2. Firebase Console → Authentication → Users에서 본인 UID를 복사합니다.
3. Build → Firestore Database → 데이터에서 `serviceAccess` 컬렉션을 만들고 문서 ID를 `administrators`로 지정합니다.
4. 필드 이름 `uids`, 유형 `array`를 추가하고 첫 항목을 **string** 유형의 본인 UID로 저장합니다. 쉼표로 연결한 문자열이 아닙니다.
5. 변경된 서버 코드를 한 번 재시작한 후 서비스의 내 정보를 다시 엽니다. 관리자 권한 관리 영역이 나타납니다.

```json
{ "uids": ["최초_관리자의_Firebase_UID"] }
```

이후 관리자는 내 정보 → 관리자 권한 관리에서 대상 회원 UID를 입력하여 부여·해제할 수 있습니다. 대상 UID는 Authentication → Users에서 확인합니다. 변경은 서버 재시작·재로그인 없이 다음 서버 요청부터 반영되며, 이미 열린 내 정보 화면은 다시 열어 갱신합니다. 권한 정보는 브라우저·표시 이름·Auth 프로필이나 custom claims를 신뢰하지 않고 매번 Firestore에서 확인합니다.

- 이메일 인증된 활성 Firebase 계정에만 관리자 권한을 부여합니다. 탈퇴 중인 계정은 변경하지 않습니다.
- 서버 트랜잭션 안에서 수행자의 최신 권한을 재확인합니다. 일반 회원은 변경 API를 사용할 수 없습니다.
- 마지막 관리자 해제를 금지하며 동시 변경도 같은 권한 문서를 통해 직렬화합니다. 현재 최대 100명입니다.
- 관리자는 탈퇴 전에 다른 관리자에게 본인의 권한 해제를 요청해야 합니다. 유일한 관리자라면 먼저 다른 관리자를 지정합니다.
- 권한 변경과 감사 기록(`adminRoleChanges`: 수행자·대상 UID, 역할, 시각)은 한 트랜잭션으로 저장합니다. 감사 기록의 운영 보유기간은 별도로 정해야 합니다.
- Firestore 연결 실패·잘못된 `uids` 형식에서는 권한을 허용하지 않습니다. 문서가 없으면 모두 일반 회원입니다.
- Firestore 규칙은 기존 브라우저 읽기·쓰기 전면 금지를 유지합니다. 콘솔과 서버 서비스 계정만 이 자료를 관리하며, 브라우저에서 직접 역할을 수정하도록 규칙을 열면 안 됩니다.
- 콘솔/IAM 권한을 가진 프로젝트 소유자는 서버 보호 규칙을 우회해 수정할 수 있으므로 별도로 접근을 관리해야 합니다. 실수로 관리자를 모두 지운 경우 소유자가 콘솔에서 복구합니다.

커뮤니티 게시글·댓글·신고 처리·정지·삭제 관리 기능은 아직 구현하지 않았습니다. 향후 서버 API에서 `AdminAccess.requireAdmin(authorization)`으로 보호해야 합니다. 관리자도 이름 금지·7일 제한을 동일하게 적용받습니다.

## API

| API | 역할 |
| --- | --- |
| `GET /api/v1/danawa/display-name-policy` | 공개 이름 규칙 조회 |
| `GET /api/v1/me/profile` | 본인의 공식 이름·권한·다음 변경 시각 |
| `PATCH /api/v1/me/profile` | `{ "displayName": "이름" }`만 허용 |
| `GET /api/v1/admin/status` | 관리자 전용 권한 확인 |
| `PUT /api/v1/admin/members/{uid}/role` | 관리자만 `{ "role": "ADMIN" 또는 "MEMBER" }` 변경 |

## 사용자 확인

1. 새 계정으로 일반 이름 등록·가입 완료를 확인합니다.
2. 금지 이름과 공백·구두점 변형을 입력하면 가입·변경이 차단되는지 확인합니다.
3. 등록 후 7일 이내 다른 이름 변경이 서버에서 409로 거부되는지 확인합니다.
4. 동일 이름 재요청은 성공하지만 변경 시각이 달라지지 않는지 확인합니다.
5. Firebase에서 등록한 관리자와 일반 회원으로 각각 관리자 API 접근을 확인합니다. 다른 회원을 관리자로 부여·해제한 뒤 해당 계정의 권한을 다시 확인합니다. 마지막 관리자 해제는 409여야 합니다.
6. 프론트엔드에서 역할을 변경하거나 Firebase 이름을 직접 바꿔도 서버 이름·권한이 변하지 않는지 확인합니다.

빌드·테스트·서버 실행은 사용자가 진행합니다. 추가한 테스트 소스를 실행하려면:

```powershell
cd E:\github\codyssey_final\backend\api
mvn '-Dtest=DisplayNamePolicyTest,AdminAccessTest,MemberProfileControllerTest' test
```
