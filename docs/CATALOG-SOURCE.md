# 저장 스냅샷을 가격 조회 소스로 사용하기

코드·테스트·명세를 작성했으며 실행·빌드·테스트는 수행하지 않았다. 기존 환경은 기본 파일 모드를 유지한다.

## 모드와 초기 실행

- `CATALOG_SOURCE=fixture` (기본): 기존 파일 가격을 조회한다. 상품 조회만 사용할 때 Firebase Emulator가 필요 없다.
- `CATALOG_SOURCE=snapshot`: Firestore Emulator에 보관된 스냅샷에서 상품별 가격 근거를 선택한다. 상품 ID·옵션·카테고리 메타데이터와 수집 원본 버전은 계속 fixture 파일에서 관리한다. 이 모드는 시작 시 에뮬레이터를 읽으므로 에뮬레이터를 먼저 실행해야 한다.

`DATA_PROVIDER=fixture`, `APP_ENV=development`는 유지한다. 데이터는 여전히 합성 fixture이며 Reef·Gemini·클라우드 연결은 없다. Spring은 .env 파일을 자동으로 읽지 않으므로 API 터미널에 환경 변수를 설정한다.

Firebase 에뮬레이터는 기존 FIREBASE.md 명령을 사용한다. 가격 저장 기록을 유지하려면 내보내기/가져오기를 사용한다. 그다음 API 터미널:

```powershell
cd D:\github\codyssey_final\backend\api
$env:CATALOG_SOURCE = 'snapshot'
$env:FIREBASE_MODE = 'emulator'
$env:FIREBASE_PROJECT_ID = 'demo-prizm'
$env:FIREBASE_AUTH_EMULATOR_HOST = '127.0.0.1:9099'
$env:FIRESTORE_EMULATOR_HOST = '127.0.0.1:8085'
# 기존 INTERNAL_API_KEY·AI_URL·COLLECTOR_URL·fixture 설정 유지
mvn test
mvn spring-boot:run
```

별도 터미널에서 기존 Node `npm start`, React `npm run dev -- --host 127.0.0.1 --port 5173`를 실행한다. 분석까지 확인하려면 FastAPI도 기존 명령으로 실행한다. 프론트 빌드 확인은 frontend에서 `npm run build`를 직접 수행한다.

저장된 스냅샷이 없어도 API는 시작하지만 해당 상품의 현재가·판매처·이력은 비어 있다. 화면은 “저장된 가격 근거 없음”을 표시하며 파일의 가격으로 대체하지 않는다. 상품 설명·옵션·카테고리와 합성 리뷰는 파일 메타데이터이므로 보일 수 있다. 현재가로 사용하는 필드는 currentPrice이며 원본 fixture의 basePrice는 현재가 대체 값이 아니다.

검색 화면의 “스냅샷 저장”으로 원하는 상품을 보관하면 같은 API 프로세스가 저장 후 조회 근거도 다시 선택한다. 따라서 비어 있는 에뮬레이터에서 시작해도 소니만 저장 → 소니만 가격 표시, 다른 상품은 근거 없음 상태로 확인할 수 있다. 전체 상품은 빈 검색어로 저장한다.

## 선택·검증 규칙

1. 현재 파일 카탈로그의 상품별 후보를 한 Firestore 트랜잭션에서 읽는다. 상품별 100개, 전체 20개 상품, 상품 내용 256 KiB, 조회 내용 합계 8 MiB 한도를 넘으면 409로 중단한다. 한도에 맞추려고 임의로 후보를 잘라 선택하지 않는다.
2. 문서 schemaVersion=1, 내용 해시/문서 ID 일치, fixture 출처·합성 표시, 내용의 상품 ID를 검사한다. 다른 옵션의 유효한 보관 내용은 선택에서 제외한다.
3. 같은 옵션 후보는 카테고리·금액·재고 상태·배송비/null·상품 참조·날짜 중복·관측 시각을 DataPolicy로 다시 검증한다. 잘못된 해시나 동일 옵션의 잘못된 근거를 무시하고 더 오래된 문서를 선택하지 않는다. 갱신 전체를 실패시킨다.
4. 후보의 **가장 최근 판매처 observedAt** 내림차순 → **일별 집계 버전** 내림차순 → **마지막 일 대표값 날짜** 내림차순 → **내용 해시** 내림차순으로 하나를 고른다. 집계 버전이 없는 기존 근거는 0으로 취급한다. 보관 createdAt은 선택 기준이 아니다. 판매처가 없는 후보의 관측 순위는 판매처 관측이 있는 후보보다 뒤다.
5. 선택한 문서의 판매처 배열과 일 대표값 배열을 한 묶음으로 사용한다. 다른 버전의 판매처·이력을 합치거나 같은 날짜를 중복 집계하지 않는다. 가격 비교·일수/평균·만료 판단은 기존 도메인 규칙을 따른다. 저장된 내용 자체는 수정하지 않는다.

모든 상품의 검증·선택이 성공한 뒤 전체 조회 뷰를 교체한다. GET 요청 안에서는 그 요청이 시작한 뷰를 고정한다. 가격 관측 함수, 비동기 분석, 채팅의 가격 답변 계산도 각 계산 단위의 뷰를 고정한다. 서로 다른 HTTP 요청 사이에는 갱신이 일어날 수 있으므로 여러 요청이 무조건 같은 시점이라는 뜻은 아니다.

목록·상세·판매처·차트·분석 입력·특가·알림 평가가 같은 CatalogRepository를 사용한다. 선택 ID가 달라지면 조회 버전과 상품 캐시 키·분석 입력 버전도 달라진다. 이전 버전 분석 조회는 만료로 처리하며 새 분석을 요청한다. 알림의 동일/역순 관측 시각 중복 방지와 기존 수동 평가·선택적 스케줄러 설정은 그대로다. 저장 완료 이벤트를 별도 워커가 순차 평가하며 복구·검증은 [저장 알림 안내](SNAPSHOT-ALERTS.md)를 따른다.

## 갱신과 상태 API

- `GET /api/v1/catalog-source`: 현재 메모리 조회 상태. DB를 다시 읽지 않는다.
- `POST /api/v1/catalog-source/refresh`: snapshot 모드에서 후보를 다시 읽고 선택한다. fixture 모드에서는 상태만 반환한다. 실행 중 모드를 바꾸는 API가 아니다.

응답은 `{data:{mode,dataVersion,loadedAt,selectedCount,missingCount,lastError,selections},meta}`다. selections에는 상품 ID·옵션·선택 스냅샷 ID·가장 최근 판매처 관측 시각이 있다. loadedAt은 뷰를 불러온 실제 서버 시각이며 가격 관측 시각이 아니다. 가격 유효성의 기준은 기존 합성 referenceTime이다.

가격 GET 응답의 `X-Catalog-Source`, `X-Catalog-Version`은 해당 요청에서 사용한 모드와 조회 뷰 버전이다. 상품 응답에는 snapshot 모드에서 `catalogSource`, `snapshotState=SELECTED|MISSING`, `snapshotId`도 포함한다. meta.source=fixture는 데이터의 합성 원본을 뜻하며 저장 위치와 구분한다.

조회 뷰 dataVersion과 Node 수집/저장의 원본 파일 dataVersion은 별개다. Node 재확인과 내부 스냅샷 저장에는 기존 collection-jobs 결과의 원본 버전을 사용한다. 조회 뷰 버전을 내부 저장 API의 원본 버전 대신 보내면 충돌한다.

상품·판매처·가격 이력·분석 및 특가 응답의 meta.catalogVersion도 조회 뷰 버전이다. 상세 화면은 상품·판매처·차트 병렬 응답의 버전이 다르면 재조회를 안내한다. 상품과 완료 분석의 버전이 다르면 분석을 함께 표시하지 않고 “상품·분석 다시 불러오기”를 제공한다. 갱신과 병렬 조회가 겹치는 수동 검증에서 이 안내도 확인한다.

저장 작업과 내부 저장 API는 커밋 후 snapshot 모드 조회 근거 갱신까지 성공해야 성공 응답을 반환한다. 커밋 후 갱신이 실패했다면 작업은 FAILED/내부 API는 409 또는 503일 수 있지만 데이터 저장은 이미 완료되었을 수 있다. 같은 요청을 재시도하면 영수증을 중복 처리하고 조회 반영을 다시 시도한다. READ_ONLY 재확인은 DB 조회 갱신을 수행하지 않는다.

갱신 실패 시 이미 성공한 이전 스냅샷 뷰는 유지하고 lastError와 오류 응답을 제공한다. 파일 가격으로 전환하지 않는다. snapshot 모드의 최초 시작에서 에뮬레이터·내용 검증이 실패하면 API 시작도 실패한다. 다른 API 프로세스나 도구에서 보관한 내용은 자동 폴링하지 않으며, 화면의 “저장 근거 다시 불러오기” 또는 위 POST로 반영한다.

## 직접 확인할 절차

1. snapshot 모드와 빈 에뮬레이터로 시작한다. 근거 없음 수와 각 상품의 currentPrice=null·빈 판매처/이력·판단 보류·빈 특가를 확인한다. 파일에 가격이 있어도 대체하지 않아야 한다.
2. 소니만 스냅샷 저장한다. 완료 후 선택 수 1, 나머지는 근거 없음. 목록·상세·판매처·차트의 근거가 보관 문서와 맞는지 확인한다. 다른 검색으로 나갔다 돌아오거나 새로고침해도 유지되어야 한다.
3. API 재시작 후에도 에뮬레이터를 유지하면 동일한 스냅샷을 선택한다. 같은 내용 재전송은 중복이며 뷰 버전은 불필요하게 바뀌지 않는다.
4. GET /catalog-source의 선택 ID와 상품 snapshotId를 비교한다. 여러 가격 GET 응답의 X-Catalog-Version을 확인한다. 갱신 전후 새 선택이 생기면 버전이 달라지고, 한 요청에서는 혼합되지 않아야 한다.
5. 보관된 유효한 다른 옵션 내용은 가격에 섞이지 않아야 한다. 더 나중에 보관한 오래된 관측이 새 관측을 덮어쓰지 않아야 한다. 해당 선택 경계는 작성한 단위 테스트에서도 확인한다.
6. 이미 한 번 조회 근거를 불러온 후 에뮬레이터를 내리고 화면에서 다시 불러온다. 오류와 이전 loadedAt/근거 유지 안내가 보이고 조회가 파일 가격으로 바뀌지 않아야 한다. 에뮬레이터 복구 후 다시 불러오면 정상 상태로 돌아와야 한다.
7. 별도 테스트 데이터에서 보관 내용만 바꾸고 해시를 그대로 두면 갱신은 409다. 알려진 상품·옵션이라도 미래 관측 등 잘못된 데이터는 적용되지 않아야 한다. 검증 후 원래 데이터/에뮬레이터 내보내기 파일을 복원한다.
8. 선택 근거 변경 후 분석을 새로 요청하여 새 입력을 사용하는지 확인한다. 알림은 수동 평가 또는 기존 스케줄러로 확인하며 같은 관측 시각에는 중복 생성되지 않아야 한다.

기본 동작으로 복원하려면 API를 종료하고 `$env:CATALOG_SOURCE='fixture'`로 재시작한다. 모드 변경만으로 보관 스냅샷이나 개인 데이터는 삭제하지 않는다.

작성한 테스트: 최신 관측/동률·옵션 배제·해시/미래 데이터 거부, 후보 한도·한 트랜잭션 읽기, 파일 모드의 DB 비의존, 근거 없는 상품의 가격 대체 차단, 요청/계산 단위 뷰 고정, 실패 시 이전 뷰 유지·상태 표시, 저장 후 조회 반영 호출 및 API 계약. 실제 에뮬레이터의 일관성·경합·재기동은 위 절차로 사용자가 확인한다.

참고: 조회 구현은 [Firestore Java 트랜잭션의 Query 읽기](https://docs.cloud.google.com/java/docs/reference/google-cloud-firestore/latest/com.google.cloud.firestore.Transaction)를 사용한다. 테스트나 실제 연결을 실행해 확인한 상태를 의미하지 않는다.
