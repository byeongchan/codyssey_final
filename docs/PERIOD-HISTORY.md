# 기간별 가격 이력 저장 및 AI 대체 분석

## 변경 내용

가격 흐름의 주간/월간 자료는 기존에도 `liveDisplayCache`에 저장됐지만, 이제 별도 보관용 저장소와 주기별 분석을 연결했다.

- 최신 정규화 스냅샷: `livePriceHistories/reef-danawa_{productId}`
- 원본 주기별 가격: 위 문서 아래 `daily/{YYYY-MM-DD}`, `weekly/{YYYY-MM-DD}`, `monthly/{YYYY-MM}`
- 저장 필드: 출처, 상품 ID, 통화, 주기, 원본 기간 날짜, 최저 표시가, 가격 조건, 원본 수집 시각(없으면 null), 수신 시각, 저장 시각, 내용 버전

가격 흐름 수집 성공 시 공유 캐시 저장과 같은 Firestore 트랜잭션에서 보관한다. 기간별 문서 ID가 같으면 최신 공급자 값으로 갱신하므로 중복 문서가 늘지 않는다. 일별 관측 컬렉션에 주간/월간 값으로 새 날짜를 만들어 넣지 않는다. 이 자료는 공용 시장 자료이며 사용자 계정 삭제 대상이 아니다.

보관용 컬렉션에는 자동 TTL을 붙이지 않았다. 다음 수집 범위에서 빠진 이전 기간 문서도 유지한다. AI는 최신 스냅샷의 주기별 범위를 사용하며, 보관된 모든 과거 문서를 자동으로 합쳐 전체 생애 가격이라고 주장하지 않는다. 빈 최신 스냅샷과 과거 보관 표본은 별개다.

기존 캐시 자료는 가격 흐름을 다시 조회하면 보관 문서가 없는 경우 한 번 이관한다. 유효 캐시라면 Reef를 다시 호출하지 않고 이관한다. 기존 자료가 없거나 만료됐다면 기존 수집 정책에 따라 외부 호출이 발생할 수 있다. 매 캐시 적중마다 모든 가격 문서를 다시 쓰지는 않는다.

## 분석 순서

1. 최근 30일 실제 저장 일별 관측이 7일 이상이면 기존 일별 통계를 우선한다.
2. 부족하면 API가 실제 제공한 일별 값으로 같은 달력 기간의 통계를 계산한다. 최근 30일 유효 날짜 7개 이상일 때 사용한다. 관측 자료와 조건이 다른 API 일별 값을 섞어서 일수를 늘리지 않는다.
3. 일별 통계가 부족하면 API 주간 자료(최소 2개), 그 다음 월간 자료(최소 2개)를 선택한다. 제공된 API 일별 시계열이 충분하면 그 주기를 먼저 사용한다.
4. 어느 주기도 충분하지 않으면 있는 표본의 범위만 표시하고 AI 호출 없이 판단을 보류한다. 미래 날짜/월과 null 가격은 분석 표본에서 제외한다.

주간/월간 보완 분석은 **반환 표본 범위**의 최저가, 중앙값, 최근 기간 최저가, 첫 표본 대비 마지막 표본 변화율을 계산한다. 일별 30일 변동성·90일 중앙값·일별 할인 빈도로 표시하지 않는다. 실제 표본 수와 시작/끝 기간을 채팅에서 함께 표시한다.

가격 조건은 `CARD_WITH_SHIPPING`, `CARD_WITHOUT_SHIPPING`, `PERIOD_MINIMUM_UNKNOWN_SHIPPING`, `UNKNOWN`으로 구분한다. 현재가와 조건이 일치하고 현재 자료의 시각이 유효할 때만 대비 비율을 계산한다. 다나와 주/월간 최저가는 배송 조건을 보장할 수 없어 현재 카드·배송 포함 가격과의 직접 비교는 보류한다. 기간 내 흐름 자체는 제한적으로 설명한다.

원본 수집 시각이 없으면 수신 시각을 관측 시각으로 꾸미지 않는다. 이전 자료도 출처 시각과 범위를 밝힌 과거 흐름 분석에는 쓸 수 있지만 현재 가격/향후 할인 확정 근거로 취급하지 않는다. 최종 구매 판단은 기존 미검증 재고·옵션 정책에 따라 보류하며 가격 신호/기간 흐름은 참고 정보다.

## 다른 API 연결 시

현재 실제 수집기는 Reef 다나와다. 다른 공급자 API를 새로 연결한 것은 아니다. 중앙 정규화/분석 정책은 아래처럼 주기를 구분한 자료를 받도록 준비했다.

```json
{
  "productId": "123",
  "currency": "KRW",
  "priceBasis": "UNKNOWN",
  "daily": [{"date": "2026-10-01", "lowestPrice": 10000}],
  "weekly": [{"date": "2026-10-05", "lowestPrice": 9800}],
  "monthly": [{"date": "2026-09", "lowestPrice": 10500}]
}
```

위 값은 형식 예시이며 실제 시세가 아니다. 누락 주기는 빈 배열로 정규화한다. 스냅샷당 최대 일별 366/주간 52/월간 60개로 제한해 Firestore 트랜잭션 쓰기 한도 안에 둔다. 같은 스냅샷은 동일 출처/통화/상품/가격 조건을 가져야 한다. 다른 API는 인증/수집 어댑터, 상품 매핑, 출처 네임스페이스, 저장/조회 연결을 추가해야 한다. 다나와 주간/월간 자료를 가짜 일별 자료로 만드는 어댑터는 사용하지 않는다.

## 사용자 적용

추가 패키지·인덱스 배포는 필요하지 않다. Node 수집기, Spring Boot, FastAPI를 재시작하고 프론트엔드를 새로고침한다. 기존 서비스 계정과 환경 설정을 사용한다.

1. 상품 상세의 가격 흐름을 불러온다. 기존 유효 캐시가 있으면 추가 Reef 호출 없이 보관 저장되는지 확인한다.
2. Firebase 콘솔에서 `livePriceHistories`의 해당 문서와 `weekly`/`monthly` 하위 컬렉션을 확인한다. `daily`는 실제 값이 없으면 비어 있어야 한다.
3. 로그인 후 ‘가격 흐름은 어떤가요?’를 질문한다. 일별 관측이 없어도 주간 표본이 충분하면 주간 보완 분석, 주간이 없으면 월간 보완 분석이 표시되는지 확인한다.
4. 채팅의 표본 수/기간/최저가·중앙값이 해당 API 자료와 일치하고 일별 통계의 부족 상태와 구분되는지 확인한다.
5. 수집 갱신 후 이력 버전과 AI 캐시 키가 바뀌는지 확인한다. 중복 수집에서 같은 기간 문서가 추가 생성되지 않아야 한다.

테스트 소스는 주기 우선순위, 미래 표본 제외, null 보존, 상품 ID 검증, 보관 경로 및 일별 관측과의 분리를 다룬다. 사용자가 직접 실행:

```powershell
# backend/api
mvn test
# backend/collector
npm test
# frontend
npm run build
```

이번 변경은 코드·구문·계약을 검토했으며 실행·빌드·테스트·실제 데이터베이스 쓰기·유료 API 호출은 하지 않았다.
